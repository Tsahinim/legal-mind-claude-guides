בחירת סביבת העבודה והפעלת משימת Cowork ראשונה

מה תוכלו לבצע בסיום החלק

בסיום החלק תהיה בידיכם סביבת ניסיון נקייה, תוכלו להסביר מדוע המשימה מתאימה ל-Cowork ולא לשיחה רגילה, ותשלחו משימה ראשונה שמסתיימת בהצגת תוכנית עבודה בלבד.

נקודת המוצא של המדריך היא החלטה מקצועית: איזה סוג עבודה ראוי למסור לסוכן שמסוגל לקרוא קבצים, להפעיל כלים וליצור תוצרים, ובאילו תנאים.

בסיום תוכלו:

  1. להבחין בין Chat, Project, Cowork ו-Claude Code ברמה הנדרשת לעבודה משפטית.
  2. להחליט אם המשימה מתאימה ל-Cowork עוד לפני חיבור קובץ.
  3. לבדוק שאתם פועלים בחשבון ובמסגרת הארגונית הנכונים.
  4. להתקין או לעדכן את Claude Desktop כאשר נדרשת גישה מקומית.
  5. להכין תיקיית תרגול שלא כוללת חומר לקוח.
  6. לבחור מצב אישור שמאפשר פיקוח אנושי.
  7. לבקש מ-Claude תוכנית עבודה בלי לאפשר ביצוע.
  8. לזהות מתי צריך לעצור, לתקן את ההיקף או לא לאשר.

שער בטיחות של Legal Mind
אין להתחיל את הלמידה על תיק אמיתי. אישור ארגוני להשתמש ב-Claude אינו אישור אוטומטי לעבד כל מסמך, ואינו קובע כשלעצמו שחיסיון, סודיות או דרישות רגולטוריות נשמרים בכל עניין. תרגול ראשון מבצעים על מסמכים מדומים ובתיקייה ייעודית.

1. בחירת סביבת העבודה לפי סוג המשימה: Chat, Project, Cowork או Claude Code

הכשל הראשוני בעבודה עם Cowork אינו בהכרח טכני. במקרים רבים הוא נובע מבחירה שאינה מתאימה לסוג המשימה.

לפני פתיחת Cowork שאלו: מה אני מבקש מ-Claude לעשות?

1.1 Chat - כאשר צריך תשובה או חשיבה משותפת

שיחה רגילה מתאימה כאשר התוצאה נשארת בתוך השיחה:

  • ניסוח חלופות לפסקה.
  • הסבר של סעיף.
  • בניית רשימת שאלות ללקוח.
  • השוואת גישות.
  • דיון בסיכונים.
  • תכנון ראשוני לפני הגדרת עבודה.

דוגמה:

הצע שלוש דרכים ענייניות לנסח את מטרת מכתב הדרישה, בלי לקבוע שכבר הוכחה הפרה.

אין כאן צורך בתיקייה, ביצירת קובץ או בהרשאת כתיבה.

1.2 Project - כאשר צריך הקשר מתמשך

Project מתאים כאשר רוצים לשמור יחד שיחות, קבצים, הוראות והקשר של נושא מתמשך. הוא שימושי למחקר, להכנת חומרים חוזרים או לעבודה מצטברת סביב תחום מסוים.

Project אינו מיועד בהכרח לביצוע פעולה במחשב. תפקידו המרכזי הוא לשמר הקשר מתמשך.

1.3 Cowork - כאשר צריך להשלים עבודה

Cowork מתאים כאשר מבקשים תוצאה מעשית שדורשת רצף פעולות, למשל:

  • לקרוא כמה קבצים.
  • להשוות בין גרסאות.
  • ליצור מסמך חדש.
  • לשמור תוצר בתיקיית פלט.
  • לבצע בדיקות לפני שמירה.
  • לדווח מה נקרא, מה נוצר ומה נשאר לבדיקה.

דוגמה:

קרא את ההסכם ואת התוספת, צור טבלה שמפרידה בין המועד המקורי למועד המעודכן, ושמור מסמך Word חדש בתיקיית הפלט. אל תשנה את קובצי המקור.

בקשה זו היא משימת ביצוע, ולא שאלה בלבד.

1.4 Claude Code - כאשר מרכז העבודה הוא קוד ומערכת קבצים טכנית

Claude Code מיועד בעיקר לעבודה עם קוד, מאגרים, טרמינל ותהליכי פיתוח. הוא יכול להיות רלוונטי ל-Legal Tech, לבניית כלי פנימי או לאתר מדריכים, אך אינו נקודת הפתיחה של עורך דין שרוצה לעבד מסמכים משפטיים.

1.5 מה Cowork מסוגל לבצע ומה עדיין מחייב בדיקה אנושית

Cowork מסוגל לפרק משימה לשלבים, לקרוא מקורות שאושרו, להשתמש בכלים זמינים, ליצור קובץ ולדווח על פעולותיו. הוא אינו יודע מעצמו אילו מסמכים מותר למסור לעיבוד, אינו קובע אם מקור אמין, ואינו הופך טיוטה לתוצר משפטי מאושר.

Cowork גם אינו מחליף מערכת ניהול מסמכים משרדית. הוא יכול לעבוד בתוך תיקייה או Project, אך מעמדו הקנוני של מסמך, מדיניות השמירה, הרשאות הצוות והחלטת ההפצה ממשיכים להיקבע בידי המשרד.

לפני בחירה ב-Cowork בדקו שלושה תנאים מצטברים:

  1. קיימת תוצאה מעשית שניתן להגדיר ולבדוק.
  2. אפשר לצמצם את המקורות, הכלים והפעולות להיקף ברור.
  3. אדם מוסמך יבדוק את התוצר לפני הסתמכות או הפצה.

כאשר אחד התנאים אינו מתקיים, נשארים בשלב ההגדרה ב-Chat או עוצרים את התהליך.

בדיקת התאמה מהירה
אם אתם צריכים תשובה - התחילו ב-Chat.
אם אתם צריכים הקשר מתמשך - בחנו Project.
אם אתם צריכים תוצאה שנוצרת באמצעות כמה פעולות - בחנו Cowork.
אם עיקר העבודה הוא קוד או מאגר טכני - בחנו Claude Code.

2. קביעת גבולות הגישה והאחריות לפני חיבור חומר משפטי

Cowork הוא סביבת עבודה סוכנית. Claude יכול לקרוא, ליצור, לערוך ולהפעיל כלים בהתאם להרשאות שניתנו לו. יכולת זו היא מקור התועלת של Cowork, והיא גם מחייבת הגדרה מוקדמת של גבולות הפעולה.

2.1 קביעת היקף המידע, הפעולות והאחריות המקצועית

לפני חיבור תיקייה, קבעו:

מה Claude רשאי לראות
  • אילו קבצים נדרשים למשימה.
  • אילו קבצים אינם נדרשים.
  • האם קיימים פרטים אישיים, סודות מסחריים או מידע חסוי.
  • האם מדיניות המשרד מתירה עיבוד של סוג המידע הזה.
מה Claude רשאי לעשות
  • קריאה בלבד.
  • יצירת קובץ חדש.
  • עריכת עותק עבודה.
  • שימוש ב-Connector.
  • גלישה.
  • פעולה חיצונית כמו שליחת הודעה או יצירת אירוע.
מה נשאר באחריות עורך הדין
  • קביעת המטרה.
  • בחירת המקורות.
  • החלטה אם לתת גישה.
  • אישור פעולות.
  • בדיקת הדיוק.
  • ניתוח משפטי.
  • החלטה אם להפיץ או להסתמך על התוצר.

2.2 חיסיון והרשאות אינם נפתרים באמצעות פרומפט

כתיבה בפרומפט:

שמור על סודיות

אינה מחליפה בחירת חשבון מתאים, תנאים מסחריים, הרשאות ארגוניות, תיקייה מצומצמת ומדיניות משרדית.

לפי Anthropic, שימוש משפטי אחראי תלוי הן בהגדרות הסביבה והן בדרך העבודה בפועל: בחירת מסגרת עבודה מתאימה, שמירת עורך הדין בתהליך, אימות מול מקורות ותיעוד השימוש. המסקנה למדריך אינה ש"כל חומר מותר", אלא שכל משרד צריך לקבוע מה מותר בהתאם לדין, להסכמים, למדיניות ולרגישות העניין.

המסמך הרשמי של Anthropic בנושא עבודה משפטית מציג את עמדת החברה ואינו חוות דעת משפטית. תנאים מסחריים, DPA, מדיניות שמירת מידע או שימוש במסגרת Team אינם קובעים לבדם שהשימוש מותר או שהחיסיון נשמר. לפני עיבוד חומר אמיתי יש לבדוק, לפי העניין והדין החל:

  • האם תנאי ההתקשרות וסוג החשבון אושרו לשימוש המשפטי המתוכנן.
  • האם קיימת התחייבות ללקוח, לצד אחר, לבית משפט או לרשות שמגבילה שימוש בכלי חיצוני.
  • האם נדרש יידוע או אישור לקוח בהתאם לדין, לכללי האתיקה או לנוהל המשרד.
  • האם מדיניות השמירה, מיקום העיבוד והגישה האנושית האפשרית מתאימים לרגישות החומר.
  • מי מוסמך לאשר את השימוש ומי אחראי לפקח על התוצר.

כאשר אחת השאלות אינה פתורה, אין להעלות את החומר עד לקבלת החלטה מוסמכת.

2.3 Cowork מרוחק והגישה למחשב

כאשר ההפעלה המרוחקת זמינה בחשבון, משימות Cowork רצות מרחוק כברירת מחדל: לולאת הסוכן והרצת הקוד פועלות בתשתית Anthropic, והמשימה והקבצים נשמרים בחשבון Claude. הפעלה מקומית עדיין קיימת בהתקנות Desktop מסוימות. לפני חיבור חומר משפטי יש לבדוק באיזה מצב פועלת המשימה בפועל.

כאשר משימה מרוחקת פותחת קובץ מקומי באמצעות Claude Desktop, תוכן הקובץ מעובד בתשתית Anthropic ולא נשאר רק במחשב. המשימה יכולה להגיע לקובץ המקומי רק כאשר Desktop פתוח ומחובר ורק בתוך תיקיות שחוברו. גם בהרצה מקומית, Connector או שירות חיצוני עשויים להעביר מידע מחוץ למחשב בהתאם לשירות ולהרשאות.

מכאן נובעים ארבעה כללים:

  1. אין להסיק ממיקום הקובץ היכן הוא יעובד.
  2. בודקים אם ההרצה מרוחקת או מקומית לפני מסירת חומר.
  3. בודקים את החיבורים, הרשאות הרשת ומדיניות הארגון.
  4. Claude אינו מקבל גישה אוטומטית לכל המחשב, אך הוא יכול להגיע לתיקיות, לכלים וליישומים שחוברו או אושרו.

לכן מחברים תיקיית משימה, לא את שולחן העבודה כולו.

טעות נפוצה
"אחבר תיקייה רחבה ואגביל בפרומפט את השימוש לקובץ אחד."
גישה זו אינה מספקת. יש לצמצם מראש את הגישה הטכנית, ולא להסתמך על הוראה מילולית בלבד.

3. בדיקת סביבת העבודה הארגונית

לפני התקנה או חיבור תיקייה, ודאו שאתם יודעים באיזו מסגרת אתם עובדים.

3.1 חשבון פרטי לעומת מסגרת Team

במשרד עורכי דין, המטרה היא לעבוד במסגרת הארגונית שאושרה לשימוש. לכן בדקו:

  • איזה שם ארגון מופיע בחשבון.
  • האם אתם בתוך חשבון פרטי או בתוך Team.
  • האם המשתמש שלכם פעיל בארגון.
  • האם Cowork מותר ברמת הארגון.
  • מי מוסמך לשנות את ההגדרה.

ב-Team, Cowork זמין ברמת הארגון ויכול להיות מושבת בידי Owner או Primary Owner. משתמש רגיל אינו צריך לנסות לעקוף את ההגדרה.

3.2 כאשר Cowork אינו מופיע

בדקו לפי הסדר:

  1. האם החשבון נמצא בתוכנית בתשלום.
  2. האם אתם בתוך המסגרת הארגונית הנכונה.
  3. האם Claude Desktop מעודכן.

לאחר שההתקנה קיימת - ארבע בדיקות לפני המשך

הערה: מדריכי רפרנס ותמונות ישנות עשויים להציג לשונית Cowork נפרדת. בממשק העדכני Chat ו-Cowork חולקים מסך בית, ובחירת המצב נעשית ליד תיבת ההודעה.

6.3 בחירת מצב אישור

מצבי האישור העדכניים כוללים:

  • Manually approve (Manual) - Claude עוצר לפני פעולה שמחייבת אישור ומציג בקשת Allow או Deny.
  • Automatically approve (Auto) - Claude ממשיך בלי לעצור בכל שלב ומפעיל בדיקת בטיחות אוטומטית לפני פעולות. Anthropic מדגישה שהבדיקה אינה הגנה מושלמת ואינה מחליפה שיקול דעת אנושי.
  • Skip all approvals (Skip) - Claude אינו עוצר ואין בדיקת בטיחות אוטומטית לכל פעולה. מצב זה אינו מתאים לתרגול משפטי.

בכל מצב, מחיקה קבועה של קובץ מחייבת אישור מפורש. לתרגול משפטי מתחילים ב-Manually approve (Manual).

אם מצב האישור אינו מוצג או שאינכם יכולים לוודא מהו המצב הפעיל, אל תשלחו את המשימה. פתחו את בורר מצב האישור ליד תיבת ההודעה ובחרו במפורש Manually approve (Manual).

לפני Allow בדקו:

  1. מה הפעולה.
  2. באיזה כלי או קובץ היא נוגעת.
  3. האם היא נכללה בתוכנית.
  4. האם היא נדרשת לתוצאה.
  5. האם אפשר לבטל אותה.
  6. האם היקף הגישה התרחב.

אישור פעולה אחת אינו אישור פתוח לכל מה ש-Claude ירצה לבצע בהמשך.

מה תוכלו לבצע בסיום החלק

בסיום החלק תעמוד לרשותכם סביבת עבודה שמבנהּ ומעמד הקבצים בה ברורים גם בחלוף זמן וגם לאדם נוסף בצוות. תוכלו לזהות היכן נמצאים המקורות, מה Claude רשאי לבצע, איזה קובץ יצר, מה עבר בדיקה אנושית ואילו הוראות חלות על כל משימה.

המדריך עוסק בשאלה שלעתים נראית טכנית, אך היא מקצועית לחלוטין: כיצד מונעים ערבוב בין חומר שהתקבל מהלקוח, חומר שעובד באמצעות Claude ותוצר שעורך דין כבר בדק.

  4. ליצור Project ייעודי בלי לערבב בין לקוחות או עניינים.
  5. לקבוע שמות קבצים וגרסאות שמאפשרים מעקב.
  6. לשמור את פלט Claude ללא שינוי לצד תוצר שנבדק.

שער בטיחות של Legal Mind

1. הסיכונים שנוצרים כאשר מקור, פלט וגרסה בדוקה אינם מופרדים

יצירה מהירה של מסמך עלולה לטשטש את מקורו של כל חלק בתוצר. בתיק משפטי, טשטוש זה עלול ליצור ארבע טעויות שונות:

  1. מקור שהתקבל מהלקוח נערך בלי שנשמר עותק נקי.
  2. טיוטה שיצר Claude נראית כאילו כבר אושרה.
  3. קובץ שנבדק נשמר באותו שם של הפלט המקורי ואין דרך להבין מה השתנה.
  4. הוראות מתיק אחד ממשיכות להשפיע על תיק אחר.

לכן סביבת עבודה תקינה אינה מסתכמת בסידור תיקיות. היא נועדה לייצר שרשרת אחריות שניתן לעקוב אחריה.

בכל רגע צריך להיות אפשרי לענות על השאלות הבאות:

  • מהו חומר המקור?
  • מי יצר את הקובץ הנוכחי?
  • האם הוא עבר בדיקה אנושית?
  • אילו הוראות חלו בעת יצירתו?
  • באילו מקורות נעשה שימוש?
  • מה אסור להעביר ללקוח או לצד אחר?

אם המבנה אינו מאפשר לענות על השאלות האלה, הוא עדיין אינו מוכן לעבודה משפטית.

2.1 הקמת המבנה ושמירה על קובצי המקור

את סביבת התרגול המלאה, כולל ארבעת מסמכי הדמה של תיק אלומה, תיצרו בעצמכם בסעיף 7 שבהמשך - כל התכנים מופיעים שם מוכנים להעתקה. לאחר היצירה אין להחליף את המסמכים ואין לשנות את תוכנם: התרגילים ובדיקות האיכות במדריך הבא מפנים לתאריכים, לסכומים ולסעיפים המופיעים בהם.

כללי היסוד לאורך כל התרגול:

  1. קובצי המקור נוצרים פעם אחת, ומאותו רגע לא נוגעים בהם יותר.

  3. לא משנים את שמות ארבעת קובצי המקור עד להשלמת התרגיל.
  4. בהרצה חוזרת שומרים את תוצרי ההרצה הקודמת בצד, ולא מוחקים אותם.

אם המבנה אינו תואם למוצג במדריך, עצרו לפני חיבורו ל-Cowork.

3. חמש שכבות ההוראה והמיקום המתאים לכל כלל

Cowork יכול לקבל הוראות מכמה מקומות. הטעות הנפוצה היא לכתוב את אותו כלל בכל מקום או להכניס מידע של תיק מסוים לשכבה שחלה על כל העבודה.

3.1 הוראות ארגוניות

בארגונים מסוימים מנהל המערכת יכול לקבוע הנחיות כלליות. הן עשויות לחול לצד ההוראות האישיות והוראות ה-Project.

אין להניח שלמשתמש יש סמכות לשנות אותן. כאשר הוראה ארגונית אינה ברורה או מתנגשת במשימה, פונים לגורם המוסמך.

3.2 הוראות גלובליות (Global instructions)

אלה כללים קבועים שחלים על כל משימות Cowork של המשתמש.

מתאים לכתוב בהם:

  • שפת עבודה מועדפת.
  • אופן הצגת אי-ודאות.
  • דרישה לציין מקורות.
  • איסור מחיקה ללא אישור.
  • העדפת יצירת קובץ חדש על פני שינוי מקור.
  • דרישה לעצור לפני פעולה חיצונית.

לא מתאים לכתוב בהם:

  • שמות לקוחות.
  • עובדות תיק.
  • אסטרטגיה משפטית.
  • הוראה שמתאימה רק לפרויקט אחד.
  • רשימת מקורות של משימה מסוימת.

3.3 הוראות ה-Project (Project instructions)

Project ב-Cowork הוא סביבת עבודה ייעודית עם קבצים, הקשר, הוראות וזיכרון משלה. הוראות ה-Project מיועדות לכללים שחוזרים בכל המשימות בתוך אותו Project.

Projects זמינים במשטחי Cowork שבהם ההפעלה המרוחקת כבר נפרסה. עם זאת, Project שמקושר לתיקייה מקומית תומך במשימות Cowork דרך Desktop בלבד. במצב כזה Desktop חייב להיות פתוח כדי שהמשימה תגיע לתיקייה. מסמכים שנשמרים בחשבון והקשר של משימה מרוחקת נגישים בין המשטחים, ואילו קבצים מקומיים אינם הופכים אוטומטית לקובצי ענן.

לדוגמה:

  • סוג העניין.
  • מוסכמות שמות פנימיות.
  • תבנית קבועה לדוחות.
  • הגדרת קהל היעד של התוצרים.
  • הפניה למסמכי מדיניות או לתבנית משרדית.

אין לפתוח Project אחד בשם "לקוחות" ולהכניס אליו עניינים שונים. ההקשר והזיכרון של Project נועדו להצטבר, ולכן ערבוב לקוחות עלול לגרום לזליגת הקשר בין משימות.

3.4 הוראות התיקייה (Folder instructions)

כאשר בוחרים תיקייה מקומית, אפשר להוסיף הוראות הקשורות לעבודה באותה תיקייה. הן מתאימות לכללים תפעוליים מקומיים:

  • מהו מבנה התיקיות.
  • אילו קבצים הם מקור.
  • היכן שומרים פלט.
  • מה אסור לשנות.
  • איך לקרוא לקבצים חדשים.

לפי Anthropic, Claude יכול לעדכן הוראות התיקייה במהלך עבודה. בעבודה משפטית אין לאפשר שינוי של כלל קריטי בלי בדיקה. כאשר Claude מציע לעדכן הוראות, בודקים מה השתנה ולמה.

תבנית להוראות התיקייה משפטית
התיקייה משמשת למשימה משפטית מוגדרת בלבד.

כללי עבודה:
1. קרא רק קבצים שנכללו במפורש ברשימת המקורות של המשימה.
2. אל תשנה קובץ בתוך 01_מקור.
3. כאשר נדרשת עריכה, צור עותק בתוך 02_עותקי_עבודה.
4. שמור פלט שנוצר בידי Claude רק בתוך 03_פלט_Claude.
5. אל תשמור קובץ בתוך 04_תוצר_שנבדק. תיקייה זו מיועדת לעותק שאדם בדק.
6. אל תמחק, תעביר או תשנה שם של קובץ בלי אישור מפורש.
7. עצור כאשר חסר מקור, כאשר קובץ אינו קריא או כאשר הוראה מתנגשת בכלל אחר.

התבנית אינה מחליפה הוראות משימה. היא מגדירה את כללי העבודה הקבועים בתוך התיקייה, בעוד שהפרומפט מגדיר את התוצר והמקורות של הפעולה הנוכחית.

3.5 הוראות משימה

הפרומפט של המשימה הוא השכבה המדויקת ביותר. כאן מגדירים:

  • מה התוצאה המבוקשת.
  • אילו מקורות נקראים.
  • אילו פעולות מבוצעות.
  • היכן נשמר התוצר.
  • מה נבדק לפני השמירה.
  • מה מדווח בסיום.

טעות נפוצה
לכתוב ב-Global instructions: "בכל משימה קרא את ארבעת מסמכי תיק אלומה". זהו כלל של משימה מסוימת, לא כלל גלובלי.

3.6 טיפול בהתנגשות בין שכבות הוראה

אין להניח שהוראה מאוחרת מבטלת אוטומטית הוראה קודמת. כאשר משימת המשתמש מבקשת פעולה שאסורה בהוראות הארגוניות, ב-Project או בתיקייה, התגובה הנכונה היא עצירה והצגת ההתנגשות.

דוגמה: הפרומפט מבקש לערוך את ההסכם, אך הוראות התיקייה אוסרות שינוי ב-01_מקור. במקרה כזה אין "לפרש" את הפרומפט כאישור. מבקשים החלטה חדשה: ליצור עותק עבודה, לשנות את יעד השמירה או לבטל את הפעולה.

פרוטוקול קצר להתנגשות:

  1. לציין אילו שתי הוראות מתנגשות.
  2. להסביר איזו פעולה אינה ניתנת לביצוע במסגרת הקיימת.
  3. להציע חלופה מצומצמת שאינה משנה את המקור.
  4. להמתין לאישור מפורש לפני המשך.

4. הגדרת Global instructions לכללי עבודה משפטיים קבועים

פתחו:

Settings > Cowork > Global instructions

העתיקו את התבנית הבאה והתאימו רק כללים כלליים שמקובלים במשרד:

אני עובד כעורך דין במסגרת ארגונית.

כללי עבודה קבועים:

1. כתוב בעברית ברורה ומקצועית, אלא אם ביקשתי שפה אחרת.
2. אל תציג טענה, רישום ניהולי או הנחה כעובדה מאומתת.
3. כאשר התוצר מבוסס על מסמכים, ציין לכל קביעה מהותית את המקור או את העוגן שנקבע במשימה.
4. כאשר המידע אינו מספיק, כתוב במפורש שלא ניתן לקבוע מהחומר הקיים.
5. אל תציג מסקנה משפטית, קביעה בדבר סמכות, אחריות או תוקף של פעולה כאילו היא הכרעה מוסמכת. גם כאשר התבקשה טיוטת ניתוח משפטי, הצג את המקורות, ההנחות, אי-הוודאות והחלופות, והבהר שנדרשת בדיקת עורך דין.
6. העדף ליצור קובץ חדש על פני שינוי מסמך מקור.
7. אל תמחק, תעביר, תשנה שם או תחליף קובץ קיים בלי אישור מפורש.
8. לפני פעולה חיצונית או פעולה שקשה לבטל, הצג מה יבוצע והמתן לאישור.
9. אל תשתמש במקור, Connector, דוא"ל, אתר או כלי שלא נדרשו למשימה.
10. בסיום משימה ציין מה נקרא, מה נוצר, היכן נשמר, באילו כלים השתמשת ומה נשאר לבדיקה אנושית.
11. תוצר שנוצר על ידך הוא טיוטת עבודה עד שעורך דין בדק ואישר אותו.

5. יצירת Project ייעודי והפרדה בין עניינים משפטיים

Projects מאפשרים לקבץ משימות קשורות בסביבת עבודה עם הוראות, קבצים, הקשר וזיכרון. הם מתאימים לעבודה מתמשכת, אך אינם מחליפים ניהול מסמכים משרדִי או הרשאות במערכת המקור.

5.1 מתי ליצור Project

צרו Project כאשר:

  • יש כמה משימות סביב אותו עניין מדומה או מאושר.
  • אותן הוראות חוזרות בכל משימה.
  • נדרש הקשר מצטבר.
  • קיימים קבצים ותבניות שרלוונטיים לכל המשימות.

אל תיצרו Project כאשר:

  • מדובר בפעולה חד-פעמית קצרה.
  • החומר שייך ללקוחות שונים.
  • לא ברור מי רשאי לראות את ההקשר.
  • אין נוהל לשמירה ולמחיקה של חומר הפרויקט.

5.2 כללים לבחירת שם Project

שם Project תקין מאפשר לזהות את מטרתו בלי לחשוף מידע מיותר.

לתרגול:

Legal Mind - סביבת אימון Cowork

בעבודה אמיתית, שם Project צריך להתאים לנוהל המשרד. אין להמציא מזהה תיק חדש כאשר קיימת מערכת קנונית לניהול עניינים.

5.3 יצירת Project מקומי לתרגול

התרגיל בסדרה משתמש בתיקייה מקומית ולכן מבוצע ב-Claude Desktop. אין לבצע אותו בווב או במובייל גם כאשר Projects מופיעים שם.

ב-Cowork:

  1. פתחו Projects בסרגל הצד.
  2. לחצו על +.
  3. בחרו יצירה חדשה או שימוש בתיקייה קיימת.
  4. הגדירו שם.
  5. הוסיפו הוראות ה-Project.
  6. חברו רק את התיקייה או הקבצים שנדרשים.

לאחר היצירה ודאו שלושה דברים לפני שליחת משימה:

  1. שם ה-Project שמופיע בכותרת הוא השם שהתכוונתם ליצור.
  2. הוראות ה-Project נשמרו וניתן לפתוח אותן מחדש.
  3. לא חוברה תיקייה או קבוצת קבצים מעבר לחומר התרגול.

כאשר אחד מהתנאים אינו מתקיים, תקנו אותו לפני תחילת העבודה.

תבנית הוראות ה-Project לתרגול:

Project זה מיועד לחומר מדומה בלבד.

בכל משימה:

5.4 השפעת זיכרון ה-Project על משימות חדשות

Claude עשוי לזכור הקשר מעבודה קודמת בתוך Project. זיכרון מועיל כאשר הוא חוסך הסברים חוזרים, אך אין להסתמך עליו כמקור משפטי.

לפני משימה חדשה:

  • קבעו מחדש את רשימת המקורות.
  • אל תניחו שעובדה שנזכרה בעבר עדיין נכונה.
  • בקשו מ-Claude לציין אם הוא נשען על זיכרון ולא על קובץ שאושר.
  • אל תתייחסו לזיכרון Project כאל ראיה, מקור קנוני או תחליף לפתיחת המסמך העדכני.
  • כאשר העניין הסתיים, פעלו לפי נוהל המשרד לגבי שמירה, ארכוב ומחיקה.

ב-Project מקומי, ארכוב מסיר את המטא-נתונים שלו מהממשק אך אינו מוחק את התיקייה או הקבצים מהמחשב. ב-Project או במשימה מרוחקים, מידע שנשמר בחשבון כפוף למסלול המחיקה ולמדיניות השמירה של החשבון. סגירת עניין מחייבת בדיקה נפרדת של כל מיקום שבו נשמר מידע, ולא הסתמכות על כפתור Archive בלבד.

שער בטיחות של Legal Mind
אין לחבר שירות אמיתי רק לצורך הדגמה. משתמשים בחשבון אימון או בתיקיית ניסיון שאושרו מראש. לפני חיבור Gmail, Drive, Microsoft 365, מערכת ניהול מסמכים או כלי משפטי, בודקים הרשאות, מדיניות משרדית והאם החיבור מסוגל גם לכתוב או לפעול.

1. ההבדל בין מקור מידע לבין כלי שמורשה לבצע פעולה

כאשר Claude קורא קובץ Word מקומי, הוא ניגש למקור. כאשר הוא משתמש ב-Connector ל-Gmail, הוא עשוי לקרוא הודעות, לחפש בהן ולעתים גם ליצור טיוטה או לשלוח הודעה, בהתאם ליכולות החיבור ולהרשאות.

לכן לפני כל חיבור מגדירים שני צירים:

1.1 מה Claude יכול לראות

  • קבצים.
  • הודעות.
  • תיקיות בענן.
  • רשומות במערכת.
  • אירועים ביומן.
  • ערוצים או פרויקטים.

1.2 מה Claude יכול לעשות

  • לקרוא.
  • לחפש.
  • ליצור טיוטה.
  • לעדכן רשומה.
  • לשלוח הודעה.
  • ליצור אירוע.
  • למחוק או להעביר תוכן.

חיבור שנראה כמו "מקור מידע" עשוי לכלול גם כלי כתיבה. אין להסתפק בשם השירות. בודקים את תיאור ה-Connector ואת בקשת האישור הספציפית.

בדיקת עורך דין
גישה לקריאה יכולה לחשוף מידע. גישה לכתיבה יכולה גם לשנות מצב בעולם. שתיהן דורשות החלטה, אך פעולת כתיבה מחייבת פיקוח מחמיר יותר.

2. בחירת דרך הגישה לפי מיקום המידע וסוג הפעולה

Claude יכול לגשת למידע בכמה דרכים. הבחירה המתאימה תלויה במיקום המידע ובפעולה הנדרשת.

2.1 קובץ או תיקייה מקומיים

מתאים כאשר:

  • החומר נמצא במחשב.
  • נדרשת עבודה בתוך תיקייה ייעודית.
  • אין צורך להתחבר לשירות חיצוני.
  • רוצים לשמור תוצר לצד הקבצים המקומיים.

גישה מקומית מתבצעת דרך Claude Desktop ורק לתיקיות שחוברו. כאשר Desktop אינו פתוח, משימה מרוחקת אינה יכולה להגיע לקבצים המקומיים.

2.2 Connector מרוחק

Connector מרוחק מתאים לשירות ענן שנכנסים אליו באמצעות חשבון, לדוגמה Google Drive, Slack, Notion או שירות SaaS אחר. לאחר החיבור הוא יכול להיות זמין בווב, במובייל, ב-Cowork וב-Desktop, בכפוף לתוכנית ולמדיניות הארגון.

הגישה בפועל נקבעת לפי החשבון המחובר, הרשאות המשתמש במערכת המקור, היקפי ה-OAuth שאושרו, מדיניות הארגון והכלים שה-Connector מציג. אין להניח שהרשאות השירות וההרשאות שמופעלות בתוך Claude זהות או מצומצמות אוטומטית.

זה אינו אומר שהחיבור מצומצם אוטומטית למשימה. משתמש בעל הרשאות רחבות בשירות עלול לאפשר ל-Claude להגיע להיקף רחב. לכן יש לבדוק:

  • באיזה חשבון מתחברים.
  • אילו הרשאות קיימות בו.
  • האם קיימת תיקיית אימון ייעודית.
  • האם ה-Connector כולל פעולות כתיבה.

2.3 Desktop extension

Desktop extension מתאים לכלי שרץ מקומית או זקוק לגישת מערכת הפעלה, לדוגמה מסד נתונים מקומי, יישום שולחני או שירות שפועל ב-localhost.

הוא פועל מקומית וזמין ב-Claude Desktop וב-Claude Code, אך אינו זמין ישירות בווב או במובייל. כאשר משימה מרוחקת משתמשת ברכיב מקומי, Desktop חייב להיות פתוח והגישה עדיין כפופה להרשאות המחשב.

אין להתקין extension ממקור לא מוכר. חיבור מקומי עשוי לגשת לקבצים, לתהליכים או לשירותים במחשב.

2.4 MCP - תקן החיבור, לא הרשאה בפני עצמה

MCP הוא תקן שמאפשר ל-Claude לגלות כלים ומקורות ולהפעיל אותם באמצעות ממשק אחיד. הוא עשוי לשמש Connector מרוחק או רכיב מקומי, אך המונח MCP אינו אומר שהחיבור בטוח, רשמי או מאושר.

לפני שימוש בשרת MCP בודקים:

  • מי מפעיל אותו והיכן הוא רץ.
  • האם הוא מקומי או מרוחק.
  • אילו כלים ומקורות הוא מציג ל-Claude.
  • אילו פעולות כתיבה הוא מאפשר.
  • כיצד מתבצע אימות המשתמש.
  • האם ניתן להגביל או לבטל את הגישה.

המשמעות המעשית לעורך הדין היא שחיבור באמצעות תקן מוכר עדיין מחייב בדיקת ספק, הרשאות ומדיניות מידע.

2.5 טבלת החלטה לבחירת דרך הגישה

3. בדיקת Connector לפני מתן גישה לחשבון או למידע

פתחו:

Customize > Connectors

או פתחו את תפריט + במשימה ובחרו ניהול Connectors.

לפני Connect עברו על הרשימה הבאה:

  1. מי פרסם את החיבור.
  2. לאיזה שירות הוא מתחבר.
  3. אילו נתונים הוא יכול לקרוא.
  4. אילו פעולות הוא יכול לבצע.
  5. איזה חשבון עומד להתחבר.
  6. האם הארגון אישר את השימוש.
  7. האם קיים חשבון תרגול או אזור נתונים מצומצם.
  8. האם אפשר לנתק את החיבור לאחר התרגול.

Custom connector באמצעות MCP מרוחק עשוי להגיע משירות שלא אומת בידי Anthropic. אין לאשר חיבור כזה רק משום שנמסרה כתובת URL. החיבור נוצר מתשתית Anthropic ולא מהמחשב המקומי, ולכן שרת ה-MCP צריך להיות נגיש בהתאם לדרישות הרשת של Anthropic. נדרשת בדיקה של הגוף המפעיל, האימות, הרשאות ה-OAuth, מדיניות המידע ויכולת הכתיבה.

3.1 רצף החיבור המעשי

  1. פתחו את עמוד ה-Connector וקראו את תיאור היכולות לפני לחיצה על Connect.
  2. בחרו רק חשבון אימון או חשבון שאושר למשימה.
  3. במסך ההרשאות קראו אילו נתונים ואילו פעולות מתבקשים.
  4. אם ההרשאות רחבות יותר ממה שאושר, בטלו את החיבור. אל תשלימו אותו כדי "לבדוק אחר כך".
  5. לאחר החיבור פתחו משימת Cowork חדשה ובדקו שה-Connector מופיע ברשימת הכלים הזמינים.
  6. הפעילו תחילה את פרומפט בדיקת הגבול שלהלן, ולא משימת תוכן.

3.3 בדיקת החיבור לאחר השימוש וניתוקו כאשר אינו נדרש

  1. האם נוצרה הרשאה קבועה בחשבון המקור.
  2. האם נשמרה גישה שאינה נדרשת עוד.
  3. האם נוצרו טיוטות, קבצים או רשומות במהלך הבדיקה.
  4. האם צריך לנתק את ה-Connector או לבטל את הרשאת ה-OAuth בשירות המקור.
  5. האם נדרש לתעד מי חיבר את השירות ולאיזו מטרה.

ניתוק מתוך Claude אינו תמיד זהה לביטול הרשאה בשירות המקור. כאשר מדובר בחשבון ארגוני, פועלים לפי נוהל המשרד ובודקים גם את מסך ההרשאות של השירות המחובר.

3.4 זיהוי Prompt Injection ותוכן חיצוני שמנסה לשנות את המשימה

מסמך, הודעת דוא"ל, אתר או רשומה בשירות מחובר עלולים לכלול הוראה שמופנית אל Claude ולא אל עורך הדין. הוראה כזאת יכולה לנסות לגרום לכלי להתעלם מהפרומפט, לחשוף מידע, להפעיל כלי נוסף או לבצע פעולה חיצונית.

לכן:

  • מתייחסים לתוכן שמגיע ממקור חיצוני כאל מידע לבדיקה, לא כאל הוראת מערכת.
  • אין לאשר מעבר לכלי, אתר או חשבון שלא נכללו בתוכנית.
  • עוצרים כאשר Claude מתחיל לעסוק בנושא שאינו קשור למשימה, מבקש סוד, קוד גישה או מידע רגיש, או מציע פעולה שלא נדרשה.
  • במשימה רגישה מצמצמים גלישה ומקורות חיצוניים למינימום ומעדיפים מקורות שנבדקו מראש.
  • לאחר התנהגות חשודה מפסיקים את המשימה, מתעדים מה נגיש ומה בוצע, ומדווחים לפי נוהל הארגון.

סינון אוטומטי או אזהרת מערכת אינם מבטלים את הסיכון. הפיקוח האנושי והצמצום הטכני נשארים חובה.

4. הגבלת הכלים הזמינים בתוך המשימה באמצעות Tool access

כאשר מחוברים שירותים רבים, אין צורך לטעון את כולם בכל שיחה. Claude מציע מצבי Tool access. המונח Auto בפרק זה מתייחס לטעינת כלים, ואינו מצב האישור Automatically approve שנלמד במדריך 1:

  • Auto - Claude מחליט אילו Connectors לטעון לפי המשימה.
  • Always available - כל החיבורים הזמינים נטענים בתחילת השיחה.
  • On demand - Claude מחפש וטוען רק את החיבור הרלוונטי כאשר הוא נדרש.

הבחירה מצמצמת אילו Connectors נטענים להקשר השיחה וכמה מקום הם תופסים. היא אינה מבטלת OAuth, אינה מנתקת Connector ואינה מצמצמת לבדה את הרשאות החשבון במערכת המקור.

4.1 בחירת מצב Tool access לפי היקף המשימה

פתחו:

+ או / > Connectors > Tool access
  • Auto הוא ברירת המחדל ומתאים כאשר Claude צריך לבחור חיבור רלוונטי לפי המשימה.
  • Always available מתאים לספרייה קטנה של חיבורים שנדרשים כמעט בכל שיחה, אך הוא טוען את כולם מראש.
  • On demand מתאים במיוחד לספרייה גדולה, משום שהחיבורים נטענים רק כאשר Claude מחפש חיבור מתאים.
  • במשימה שאסור לה להשתמש במקור חיצוני, אין להסתפק ב-On demand: חסמו את כלי ה-Connector הרלוונטיים או נתקו את החיבור בהתאם לנוהל המשרד.
  • עצם טעינת Connector אינה מעניקה לו אישור לבצע כל פעולה.

Tool access קובע מתי Connector נטען לשיחה. הרשאת OAuth קובעת לאיזה מידע החשבון יכול להגיע. הרשאת כלי בתוך Cowork קובעת אם פעולה מסוימת מותרת. אלה שלושה מנגנונים שונים.

לבדיקה מעשית, פתחו את התפריט ליד תיבת ההודעה, עברו אל Connectors > Tool access ובדקו את המצב הפעיל. לאחר מכן בדקו בנפרד אילו Connectors וכלים מותרים במשימה. אל תציגו מצב טעינה מצומצם כאילו הוא ביטל הרשאה קיימת.

4.2 בקרת אישורי כתיבה במסגרת Team

ב-Team וב-Enterprise, Owner או Primary Owner יכולים לקבוע אם משתמשים רשאים לשמור Always allow לכלים בעלי יכולת כתיבה בנתיב:

Organization settings > Cowork > Permissions > Allow "Always allow" for connector tools

ההגדרה כבויה כברירת מחדל. כאשר היא כבויה, האפשרות לאשר כלי כתיבה לכל המשימות אינה זמינה והמשתמש נדרש לאשר אותו בכל משימה. כלים לקריאה בלבד פטורים רק כאשר ה-Connector מסמן אותם במפורש כקריאה בלבד.

הגדרה זו מוסיפה נקודת בקרה, אך אינה מספיקה לבדה. אישור טכני לכלי כתיבה צריך להינתן רק לאחר בדיקת הפעולה, התוכן, הנמען, הסמכות והאפשרות לבטל את התוצאה.

טעות נפוצה
"ה-Connector כבר מחובר, לכן מותר להשתמש בו."
חיבור טכני אינו אישור מקצועי למשימה הנוכחית.

5. ההבדל בין Skill, Plugin והרשאה טכנית

5.1 Skill: ידע ונוהל עבודה שמופעלים כאשר הם רלוונטיים

Skill מעניק ל-Claude ידע מקצועי ונוהל עבודה ייעודי, והוא עשוי לכלול הוראות, קובצי עזר, דוגמאות ואף קוד. הוא נטען כאשר המשימה מתאימה לתיאור שלו, בניגוד להוראה גלובלית שחלה תמיד. Skill מתאים כאשר כבר קיימת שיטת עבודה שנבדקה, לדוגמה:

  • הפקת מפת אירועים.
  • בדיקת עקביות בין גרסאות.
  • הכנת רשימת מסמכים חסרים.
  • יצירת דוח סטטוס לפי תבנית משרדית.

Skill אינו הרשאה ל-Connector או לקובץ, אך קובצי העזר שבתוכו עשויים לשמש מקור ידע עבור התהליך. לכן בודקים את כל החבילה ולא רק את שם ה-Skill.

ב-Team, הזמינות של Skills נשלטת ברמת הארגון, ו-Owner יכול להשבית אותם. להפעלת Skills ארגוניים נדרשים גם Code execution and file creation וגם Skills בנתיב Organization settings > Skills. המשתמש מנהל Skills זמינים ב-Customize > Skills.

לפני שימוש ב-Skill:

  • קוראים את ההוראות שלו.
  • בודקים אילו כלים הוא מצפה להפעיל.
  • מוודאים שהוא מתאים לדין ולנוהל המשרד.
  • מריצים אותו על חומר מדומה.
  • לא מניחים שהוא מעודכן רק מפני שהוא מותקן.

5.2 Plugin: חבילת יכולות הכוללת כמה רכיבים

Plugin מאגד כמה רכיבים, בדרך כלל Skills, Connectors ותתי-סוכנים. הוא זמין בתוכניות בתשלום ונועד לספק סביבת עבודה מוכנה לתפקיד או לתהליך. מתקינים ובודקים אותו דרך Customize > Plugins. Skills הכלולים בו יכולים לפעול גם ב-Chat, ואילו Hooks ותתי-סוכנים פועלים רק ב-Cowork.

Plugin משפטי יכול לכלול, למשל:

  • Skill להשוואת חוזים.
  • Connector ל-SharePoint או ל-Word.
  • תת-סוכן לבדיקת ציטוטים.

התקנת Plugin אינה פעולה ניטרלית. לפני התקנה בודקים:

  1. מי יצר אותו.
  2. אילו רכיבים הוא מתקין.
  3. אילו Connectors הוא מציע לחבר.
  4. האם הוא כולל Hooks או תתי-סוכנים שפועלים ב-Cowork.
  5. האם הארגון אישר אותו.
  6. האם ניתן לקרוא את קובצי ההוראות שלו.

ב-Plugins שהמשתמש מוסיף בעצמו, הקבצים עשויים להישמר מקומית. Plugin שמופץ בידי הארגון עשוי להיות מנוהל ומעודכן בידי מנהל המערכת.

5.3 התנאים הנדרשים לפני הפיכת תהליך ל-Skill

אל תארזו תהליך ל-Skill לאחר הרצה אחת בלבד. קודם:

  • מריצים כמה פעמים.
  • מתקנים תקלות.
  • בודקים מקרי קצה.
  • מגדירים קלט ופלט.
  • קובעים נקודות אישור.
  • מוסיפים QA.

רק לאחר שהתהליך עבר מספר הרצות מתועדות, מקרי קצה ו-QA ברמה שקבע המשרד, ניתן לשקול לארוז אותו כנכס עבודה חוזר. גם לאחר האריזה נדרשים ניהול גרסאות, בדיקות תקופתיות ופיקוח על שינויים במקורות, בכלים ובדין.

6. בחירת תהליכים שמתאימים למשימות מתוזמנות

Scheduled tasks מאפשרות להריץ משימה בשעה או בקצב שנקבעו מראש. הן יכולות להשתמש ב-Connectors, ב-Skills וב-Plugins שהוגדרו.

משימה מתוזמנת אינה מתאימה לכל פעולה משפטית. ככל שהפעולה חיצונית יותר וקשה יותר לביטול, כך נדרש יותר פיקוח.

6.1 תהליכים שמתאימים לתזמון לאחר בדיקה

  • יצירת דוח פנימי מקריאה בלבד.
  • ריכוז פריטים חדשים ממקור ענן מאושר או מקבצים שנשמרו בחשבון.
  • סיכום שבועי של משימות פתוחות.
  • איתור פריטים שדורשים בדיקה אנושית.
  • הכנת טיוטה שאינה נשלחת אוטומטית.

6.2 פעולות שאינן מתאימות לתזמון בתחילת העבודה

  • שליחת הודעה לצד אחר.
  • יצירת התחייבות.
  • מחיקת קבצים.
  • שינוי רשומה קנונית.
  • הגשה או פרסום.
  • פעולה שמצריכה הכרעה משפטית בזמן אמת.

6.3 מסלול ההפעלה היציב למשימה מתוזמנת

לפי תיעוד Anthropic, Scheduled tasks רצות מרחוק ולכן אינן דורשות שהמחשב יהיה ער או ש-Claude Desktop יהיה פתוח. הן יכולות להשתמש ב-Connectors, ב-Plugins ובקבצים שנשמרו בחשבון Claude.

באותו מאמר עזרה מופיעה גם אפשרות לבחור תיקייה מקומית, עם הערה שמשימה שתלויה בקבצים או ביישומים מקומיים תרוץ מקומית. מאחר ששתי ההנחיות מופיעות כיום זו לצד זו, סדרת Legal Mind אינה מבססת את תרגיל הבסיס על תיקייה מקומית. עד לאימות חזותי בחשבון Team, מלמדים כאן רק את המסלול המרוחק שאינו תלוי במחשב.

לפני תזמון בדקו:

  • שהמשימה אינה תלויה בתיקייה או ביישום מקומיים.
  • אילו Connectors, Skills ו-Plugins זמינים בכל הרצה.
  • אילו הרשאות כתיבה או פעולה חיצונית קיימות.
  • היכן יופיע התוצר ומי יכול לגשת אליו.
  • מה קורה כאשר מקור בחשבון או Connector אינם זמינים.

6.4 תרגיל: יצירת משימה מתוזמנת מרוחקת ללא מקור חיצוני

תחילה הריצו ידנית משימה שאינה משתמשת בקובץ, ב-Connector, ב-Plugin או בגלישה:

צור טיוטת צ'ק ליסט פנימי לבקרה שבועית על משימות Cowork.

השתמש רק בהוראות שבפרומפט הזה. אל תיגש לקובץ, לתיקייה, ל-Connector, ל-Plugin, לדוא"ל או לאתר.

הטיוטה תכלול:
- תאריך הבדיקה
- משימות מתוזמנות שצריך לעבור עליהן
- הרשאות זמניות שצריך לבחון מחדש
- תוצרים שממתינים ל-QA אנושי
- תקלות או חריגות שצריך לתעד

אל תשלח הודעה, אל תעדכן מערכת ואל תמחק דבר.
הצג את הצ'ק ליסט לבדיקה אנושית בלבד.

בדקו שהפלט הוא טיוטה פנימית בלבד ושלא הופעל כלי חיצוני.

יצירת התזמון בפועל
  1. פתחו Scheduled בסרגל הצד.
  2. לחצו New task.
  3. בחרו Set up manually. לחלופין אפשר להתחיל ממשימת Cowork באמצעות הפקודה /schedule.
  4. הגדירו שם ברור למשימה.
  5. הדביקו את הפרומפט שנבדק ידנית.
  6. בחרו Manually approve (Manual).
  7. הגדירו קצב שבועי וזמן הרצה.
  8. בחרו מודל רק כאשר נדרש; זהו שדה אופציונלי.
  9. אל תבחרו תיקייה מקומית ואל תחברו Connector לתרגיל.
  10. שמרו ובדקו מתי ההרצה הבאה צפויה.

לפני יציאה מהמסך רשמו היכן יופיע הפלט ומי אחראי לבדוק את ההרצה הראשונה.

6.5 בדיקת ההרצה הראשונה וטיפול בכשל

לאחר ההרצה המתוזמנת הראשונה בדקו:

  • האם המשימה רצה במועד ובקצב שנקבעו.
  • האם התוצר הופיע בעמוד Scheduled ובמקום הצפוי.
  • האם נוצרו פריטים כפולים.
  • האם הופעל כלי, Connector או מקור שלא נכללו בתרגיל.
  • האם התקבלה תוצאה חלקית בגלל מקור בחשבון או Connector שאינם זמינים.

כאשר ההרצה אינה עומדת בדרישות, השהו את המשימה לפני תיקון הפרומפט או ההרשאות. לאחר התיקון הריצו אותה ידנית ורק אז הפעילו מחדש את לוח הזמנים.

6.6 אחריות מקצועית על תוצר של משימה מתוזמנת

הרצה שהסתיימה בהצלחה טכנית אינה תוצר משפטי שנבדק. לפני הפעלה קבועה קובעים:

  • מי אחראי לעבור על כל הרצה ובתוך איזה פרק זמן.
  • מי מחליף אותו בעת היעדרות.
  • אילו ממצאים גורמים להשבתה מיידית.
  • מתי שינוי בדין, במסמך מקור, בהרשאות או בזהות בעלי התפקידים מחייב בדיקה מחדש.
  • כיצד מתועדים הפלט, הבדיקה והתיקונים.

אין לתזמן שליחה ללקוח, לצד שכנגד, לבית משפט או לרשות, ואין לתזמן פעולה שיוצרת התחייבות או משנה רשומה קנונית, בלי מנגנון אישור נפרד של אדם בעל סמכות סמוך לפעולה.

7. הסיבה ש-Computer use אינו נלמד כתהליך עבודה במסגרת Team

Claude יכול להשתמש במסך המחשב במצב Computer use כאשר אין Connector או כלי מדויק יותר. היכולת נמצאת ב-Research Preview וזמינה כיום ב-Pro וב-Max, לא ב-Team וב-Enterprise.

לכן:

  • הסדרה אינה מלמדת Computer use כתהליך עבודה של Team.
  • אין לבנות נוהל משרדי על יכולת שאינה זמינה למסגרת היעד.
  • גם בסביבה שבה היא זמינה, Anthropic מגדירה אותה כ-Research Preview ומזהירה מפני שימוש בה לטיפול במסמכים משפטיים, חוזים ואפליקציות שמציגות מידע אישי או חסוי.
  • Computer use מצלם את המסך ופועל ישירות ביישומים ללא שכבת Sandbox ביניהם; הרשאות לכל יישום והגנות אוטומטיות אינן תחליף לסגירת חומר רגיש ולפיקוח צמוד.
  • כאשר קיים Connector מדויק ומאושר, הוא עדיף בדרך כלל על ניווט חזותי איטי ופגיע יותר לטעויות.

עיקרון הבחירה הוא:

  1. כלי מדויק ומאושר.
  2. Connector מתאים.
  3. תיקייה מקומית מוגדרת.
  4. רק לאחר מכן יכולת רחבה יותר, כאשר היא זמינה ומאושרת.

8. בדיקות חובה לפני חיבור כלי או הפעלת משימה מתוזמנת

  • החיבור נדרש למשימה מסוימת.
  • בדקתי מי פרסם אותו.
  • אני יודע איזה חשבון מתחבר.
  • בדקתי את הרשאות החשבון במערכת המקור.
  • זיהיתי אילו כלים קוראים ואילו כותבים.
  • בדקתי את מצב Tool access והבנתי שהוא אינו מבטל הרשאת OAuth.
  • חסמתי או ניתקתי Connector שאסור להשתמש בו במשימה.
  • קראתי את הוראות ה-Skill או ה-Plugin.
  • וידאתי ש-Code execution and file creation ו-Skills מופעלים כאשר נדרש Skill.
  • הארגון אישר את הרכיב.
  • בדקתי את התהליך על חומר מדומה.
  • תרגיל המשימה המתוזמנת אינו תלוי בתיקייה מקומית.
  • משימה מתוזמנת מייצרת טיוטה או דוח פנימי ולא פעולה מחייבת.
  • הוגדר אדם אחראי לבדיקת כל הרצה ולכשל שמחייב השבתה.
  • נבדק סיכון Prompt Injection ממקורות חיצוניים.
