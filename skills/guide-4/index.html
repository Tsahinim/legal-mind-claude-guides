01

לפני ההתקנה - בדיקת תנאים ונתיב הממשק העדכני

Skills דורשים הפעלה של Code execution and file creation. בחשבונות אישיים בודקים זאת ב-Settings > Capabilities.

אם אינכם מוצאים את המסך הזה

פתחו את Settings וחפשו את הלשונית Capabilities. אם היא אינה מופיעה כלל, או שהמתג מופיע אך אינו ניתן ללחיצה, המשמעות היא אחת משתיים: סוג המנוי שלכם אינו כולל את היכולת, או שאתם בחשבון ארגוני שבו ההגדרה נעולה בידי בעל הארגון.

במקרה הראשון נדרש שדרוג מנוי; בשני יש לפנות למי שמנהל את הארגון ולבקש שיפעיל את היכולת. בשני המקרים אין דרך לעקוף זאת מצד המשתמש, ואין טעם להמשיך לפרקים הבאים לפני שהיכולת פעילה.

את רשימת ה-Skills פותחים דרך Customize > Skills.

להעלאת Skill מותאם: בעמוד Customize > Skills לחצו על הכפתור שבפינה העליונה (מסומן + או Add, לפי גרסת הממשק) ובחרו Upload a skill, והעלו ZIP תקין.

צילומי מסך מהממשק הקודם

התמונות המקוריות נשמרו כדי להמחיש את רצף העבודה. שמות כפתורים ומיקומם עשויים להשתנות. בצעו את הפעולה לפי הנתיב הכתוב והעדכני בפרק זה.

הבדלים בין סוגי חשבונות

בחשבונות אישיים מפעילים Code execution and file creation דרך Settings > Capabilities. ב-Team וב-Enterprise ההפעלה וההקצאה הארגונית מנוהלות דרך Organization settings > Skills. השיתוף הארגוני תלוי בהגדרת בעל הארגון.

02

איתור אזור הסקילים

במדריך 3 בנינו סקיל שלם דרך שיחה רגילה, בלי לגעת פעם אחת בתפריט ניהול נפרד. עכשיו, כשהסקיל כבר קיים, המדריך הזה עובר לצד השני: איך רואים את כל הסקילים שלכם במקום אחד, איך מתקינים סקיל שמישהו אחר שלח לכם, ואיך מוודאים שהכול עובד כמו שצריך.

צילומי המסך משקפים את חומרי המקור ואת הממשק שהיה זמין בעת יצירתם. אם הממשק הנוכחי שונה, יש לפעול לפי נתיב הניווט הכתוב והמעודכן במדריך.

לאחר הלחיצה נפתח עמוד עם כמה כרטיסיות - Skills, Connectors, Plugins, Memory ועוד. הכרטיסייה Skills מסומנת בצד ותוביל לעמוד ניהול הסקילים:

זהו המקום היחיד במערכת שממנו מנהלים סקילים: מתקינים חדשים, רואים אילו כבר מותקנים, ומדליקים או מכבים כל אחד מהם. שווה לזכור את הנתיב הזה - Customize ← Skills - כי תחזרו אליו הרבה, לכל דבר הקשור לניהול (לא ליצירה עצמה, שיכולה לקרות גם מתוך שיחה רגילה כפי שראינו במדריך 3).

שווה גם לשים לב לכרטיסיות השכנות באותו עמוד: Connectors מחברים את סביבת העבודה לשירותים חיצוניים כמו Google Drive או Slack, ו-Memory שומר העדפות קבועות בין שיחות. Skills, Connectors ו-Plugins נראים דומים בממשק - כולם כרטיסיות תחת Customize - אך משרתים תפקידים שונים. מדריך 1 מרחיב על ההבדל בין Skill, Prompt ו-Project; Connectors ו-Plugins הם רכיבים נפרדים בממשק.

03

התקנת סקיל שהכנו

לפני שממשיכים: איזה מצב מתאר אתכם?

בניתם את הסקיל במדריך 3 דרך שיחה ולחצתם Save skill? הסקיל כבר מותקן אצלכם, ואין לכם צורך בשום קובץ ZIP. דלגו על הפרק הזה ועברו ישירות לפרק הבא.

קיבלתם קובץ ZIP מעמית, הורדתם סקיל ממקור חיצוני, או מעבירים סקיל בין חשבונות? הפרק הזה בשבילכם.

אם בניתם את ה-Skill במדריך 3 דרך שיחה ולחצתם Save, הוא כבר מותקן ואפשר לעבור לפרק הבא. אם שמרתם אותו כקובץ ZIP או קיבלתם ZIP מוכן, מתקינים אותו כך:

  1. בעמוד Customize > Skills, לחצו על כפתור Add בפינה הימנית העליונה
  2. מתוך שלוש האפשרויות שנפתחות (Create with Claude, Write skill instructions, Upload a skill) - בחרו Upload a skill
  3. בחרו את קובץ ה-ZIP מהמחשב
  4. המתינו לעיבוד - הסקיל יופיע ברשימה עם המתג שלו
  5. ודאו שהמתג דולק כדי שהסקיל יהיה זמין לשימוש

מיד אחרי ההתקנה, הסקיל מופיע בראש הרשימה שלכם - לצד סקילים אחרים שכבר היו לכם, כמו סקילי דוגמה או סקילים מובנים מ-Anthropic. זה בדיוק המקום שבו שווה לעצור רגע ולוודא שהוא אכן נטען בהצלחה, לפני שממשיכים לשלב הבדיקה עצמה.

איפה בדיוק רואים את המתג הזה? לוחצים על השורה של הסקיל עצמו ברשימה:

שימו לב שבמסך הזה רואים גם את תוכן קובץ ה-skill.md עצמו - כפי שלמדנו במדריך 3, רק שכאן רואים את הקובץ בתוך Skill מותקן.

אם אתם מתקינים כמה סקילים ברצף - למשל, כמה תהליכים שונים שהמשרד רוצה להטמיע יחד - כדאי לבדוק כל אחד בנפרד לפני שעוברים לבא בתור, ולא להתקין את כולם ואז לבדוק בסוף. כך, אם משהו משתבש, קל להצביע בדיוק על הסקיל הבעייתי, במקום לנחש איזה מבין כמה סקילים חדשים גרם לתקלה.

04

ספריית הסקילים

מעבר לסקילים שבניתם בעצמכם, קיימת ספרייה מאוחדת של Skills, Connectors ו-Plugins - ובה גם רכיבים של Anthropic ורכיבים שהארגון שלכם העמיד לרשות המשתמשים.

  1. בעמוד Customize > Skills לחצו על הכפתור Browse שבראש הרשימה, לצד כפתור ההוספה. שימו לב שזהו כפתור נפרד, ולא אחת משלוש האפשרויות שבתפריט ההוספה
  2. בחלון שנפתח, חפשו לפי שם בשדה החיפוש, או סננו/מיינו עם הכפתורים Filter by ו-Sort by
  3. בדקו מי היוצר של כל סקיל - מופיע מתחת לשם, למשל Anthropic, שם הארגון שלכם, או גורם אחר
  4. פתחו את כרטיס ה-Skill הרצוי ולחצו Install
לתשומת לבכם

סקיל מותקן מהספרייה הוא view-only - אי אפשר לערוך אותו ישירות. כדי לשנות אותו צריך להוריד אותו, לערוך, ולהעלות עותק חדש משלכם. עצם ההופעה בספרייה, דירוג גבוה, או שם מוכר - אינם הוכחה שהסקיל בטוח לשימוש עם חומר לקוח. מדריך 5 מרחיב בדיוק על איך בודקים סקיל כזה לפני שימוש אמיתי.

שימו לב שבספרייה יש הבחנה חשובה בין סקילים לפי היוצר: סקילים מתויגים "Anthropic" נבנו על ידי החברה שמפתחת את הפלטפורמה, וסקילים אחרים עשויים להיות מהארגון שלכם או מגורמים חיצוניים לגמרי. ההבחנה הזו לא הופכת סקיל של Anthropic לפטור מבדיקה - היא רק משנה את נקודת ההתחלה של הבדיקה.

ב-Team וב-Enterprise יש להבחין בין Skill ששותף ישירות עם משתמש, Skill ששותף לכל הארגון ו-Skill שבעל הארגון הקצה מרכזית. Skill ששותף ישירות מופיע ברשימת המשתמש וניתן להפעילו או להסירו מהרשימה. Skills ארגוניים מופיעים ברשימה או בספריית הארגון בהתאם לאופן ההפצה; הסרתם מספריית הארגון נעשית על ידי המשתף או בעל הרשאה ארגונית.

05

התקנת סקיל חיצוני

Skill מהספרייה מתקינים באמצעות Browse skills ו-Install. Skill שמתקבל כתיקיית ZIP מעלים באמצעות Customize > Skills > Add > Upload a skill. בשני המקרים אין להשתמש בחומר לקוח אמיתי לפני בדיקת המקור, התכולה וההרשאות.

זו בדיוק הנקודה המסוכנת: מבחינה טכנית, אין שום "אזהרה אדומה" אוטומטית שתעצור אתכם מלהתקין סקיל ממקור לא מוכר. המערכת לא יודעת להבחין בין סקיל שבניתם בעצמכם לבין סקיל שהורדתם מאתר אלמוני - ההבחנה הזו היא באחריותכם בלבד, לפני שמגיעים לכפתור ההתקנה.

חשוב לפני שימוש אמיתי

לפני שמפעילים בפועל סקיל חיצוני על חומר אמיתי מתיק לקוח, עברו על רשימת הבדיקה המלאה במדריך 5. הפעולה הטכנית פשוטה; הבדיקה שצריכה לקדום אותה היא לא.

לפני שלוחצים על כפתור ההתקנה עצמו, שווה הרגל קטן שחוסך הרבה: לעצור לרגע ולבדוק מי היוצר של הסקיל - השם שמופיע מתחת לכותרת, כפי שראינו בפרק הקודם על הספרייה. סקיל שמגיע כקובץ ZIP ששלח מישהו בדוא"ל, לעומת סקיל שנמצא דרך כפתור Browse בספרייה הרשמית, אינם אותו סיכון בדיוק - אבל שניהם דורשים את אותה בדיקה בסיסית לפני התקנה על חומר אמיתי.

06

הפעלה אוטומטית

ברירת המחדל: ב-Claude, כאשר בקשה מתאימה לתיאור של סקיל מותקן ופעיל, המערכת טוענת אותו לבד - בלי שתצטרכו לבחור אותו ידנית, ובלי שתצטרכו אפילו לדעת שהוא קיים. זו הסיבה שתיאור מדויק (כפי שראינו במדריכים 1 ו-3) קריטי: הוא המידע שהמערכת בוחנת לפני שהיא מחליטה אם לטעון את הסקיל.

בדוגמה שראינו קודם - הבקשה ליצור מכתב התראה - לא ביקשנו שום סקיל במפורש. המערכת זיהתה שהבקשה מתאימה לתיאור של סקיל ליצירת מסמכי Word, וטענה אותו לבד. זו בדיוק ההתנהגות הרצויה: אתם ממשיכים לעבוד כרגיל, בשפה טבעית, וההתאמה קורית מאחורי הקלעים.

היתרון המעשי הוא שאתם לא צריכים לזכור אילו סקילים מותקנים אצלכם כדי להשתמש בהם - זה בדיוק העיקרון של חשיפה הדרגתית שראינו במדריך 1: המערכת סורקת את כל התיאורים הקצרים בכל שיחה, וטוענת רק את מה שרלוונטי. עם זאת, כדאי לזכור שההסתמכות הזו אינה אבסולוטית: אם ניסחתם בקשה בצורה חריגה או כללית במיוחד, ייתכן שהתיאור לא יתאים, והסקיל לא ייטען למרות שהתכוונתם שהוא יפעל. במשימה קריטית או לא שגרתית, עדיף לא להסתמך רק על הזיהוי האוטומטי - אלא לוודא באמצעות הפעלה מפורשת, כפי שנראה בפרק הבא.

07

הפעלה מפורשת

לפעמים כדאי לוודא שסקיל ספציפי בהחלט ייטען, ולא להשאיר את זה לזיהוי האוטומטי בלבד - למשל כשאתם בודקים סקיל חדש ורוצים לוודא שהוא בכלל תקין, לפני שסומכים על הזיהוי האוטומטי שלו. הדרכים הבאות עובדות בממשק הנוכחי:

  • אזכור שם הסקיל בגוף הבקשה, למשל "תשתמש בסקיל legal-chronology עבור המסמכים האלה"
  • בקשה מפורשת שמתארת בדיוק את מה שהסקיל אמור לעשות, גם בלי לנקוב בשמו המדויק
  • תיאור משימה שמתאימה בבירור לתיאור הסקיל - הדרך שראינו בפועל בדוגמת מכתב ההתראה בפרק הקודם, שבו נטען סקיל docx בלי שום אזכור מפורש

בפועל, ההבדל בין הפעלה אוטומטית להפעלה מפורשת הוא רק מידת הביטחון שאתם רוצים לפני שהמשימה מתחילה. אם אתם עדיין בשלב הבדיקה של סקיל חדש, עדיף להפעיל אותו במפורש כדי לוודא שהוא בכלל תקין. אחרי שהוא הוכיח את עצמו, אפשר לסמוך על ההפעלה האוטומטית לשימוש היומיומי.

יש גם מצב ביניים שימושי: אם אינכם בטוחים אם ההפעלה תהיה אוטומטית או לא, אפשר פשוט לשאול את המערכת במפורש "אילו סקילים רלוונטיים לבקשה הזו?" לפני שמתחילים בפועל - זו דרך פשוטה לוודא הבנה הדדית בלי להתחייב לניסוח מדויק של שם הסקיל.

08

כיצד יודעים שהסקיל הופעל

כשסקיל נטען בפועל, מופיע חיווי ברור בין שלבי העבודה של המערכת - שורה שמתחילה ב-"Loaded" ואחריה שם הסקיל.

לדוגמה, בבקשה ליצור טיוטת מכתב התראה קצר ללקוח, כך נראתה תחילת התהליך בפועל:

אם שורה כזו לא מופיעה כלל, סימן שאף סקיל לא נטען - ושווה לעבור לפרק הבא כדי להבין למה.

שימו לב שיותר מסקיל אחד יכול להיטען באותה בקשה, אם היא נוגעת בכמה תחומים בו-זמנית - למשל בקשה שגם דורשת ניתוח מסמכים וגם הפקת קובץ Word, עשויה לטעון שני סקילים שונים ברצף, כל אחד עם שורת "Loaded" משלו. אם אתם לא בטוחים אילו סקילים פעלו בפועל, אפשר תמיד לפתוח את פירוט שלבי העבודה בממשק (בדרך כלל תחת חץ קטן או כותרת מתקפלת מעל התשובה) ולראות את הרשימה המלאה של הפעולות שבוצעו, כולל כל שורת טעינה.

09

כשהסקיל אינו מופעל

אם ציפיתם שסקיל ייטען ולא קרה - אתם מחפשים "Loaded [שם]" ולא מוצאים אותו - לרוב הבעיה נמצאת בתיאור של הסקיל, לא בתוכן שלו:

  • שפרו את התיאור כך שיכלול גם "מה" וגם "מתי", כפי שראינו במדריך 1
  • בדקו אם השם או התיאור כוללים מילים כלליות מדי, כמו "עוזר" או "כלי"
  • הוסיפו הקשר מפורש בבקשה עצמה - למשל את שם הסוג המדויק של המסמך
  • צמצמו עמימות - נסחו את הבקשה בצורה קונקרטית יותר במקום ניסוח כללי
  • בקשו הפעלה מפורשת (כפי שראינו בפרק הקודם) כדי לוודא שהסקיל בכלל תקין ומותקן נכון
  • בדקו שהמתג של הסקיל אכן דולק - לפעמים הפתרון פשוט כמו לחיצה אחת

לכן שווה תמיד להתחיל דווקא מהבדיקה האחרונה והפשוטה ביותר ברשימה - המתג - עוד לפני שמתחילים לשכתב תיאורים ארוכים. זו טעות נפוצה ופשוטה לפספס.

לדוגמה: אם תיאור הסקיל הוא "עוזר בהכנת מסמכים", ואתם מבקשים "תכין לי טיוטת מכתב התראה", ייתכן שהתיאור הכללי מדי לא יוצר התאמה חזקה מספיק כדי שהמערכת תבחר לטעון אותו באופן אוטומטי. תיאור מדויק יותר כמו "מנסח מכתבי התראה ללקוחות בגין חוב כספי, כולל פירוט סכום וריבית" יוצר התאמה הרבה יותר ברורה לאותה בקשה בדיוק.

10

כשהסקיל מופעל יותר מדי

הבעיה ההפוכה קורית גם היא: סקיל שנטען גם כשהוא לא באמת רלוונטי לבקשה, ולכן משפיע על התוצאה בצורה לא רצויה. הפתרון תמיד באותו כיוון - לחדד את התיאור, לא להוסיף לו עוד מילים:

  • צמצמו את התיאור כך שיתאר במדויק את הגבולות של המשימה שהוא נועד לבצע
  • הוסיפו הגדרה מפורשת של מתי לא להשתמש בו, לא רק מתי כן
  • הוסיפו תנאים ספציפיים יותר לתיאור, כדי לצמצם את טווח ההתאמה
  • אם הסקיל רחב מדי במהותו - מנסה לשרת כמה תהליכים שונים בבת אחת - שקלו לפצל אותו לשניים או שלושה סקילים ממוקדים יותר
  • הסירו מונחים כלליים מדי מהתיאור, כמו "מסמך" או "עבודה" בלי הקשר נוסף

לדוגמה: סקיל שנבנה במקור רק לניסוח מכתבי התראה ללקוחות, עם תיאור כללי מדי כמו "עוזר בכתיבת מסמכים משפטיים", עלול להיטען גם כשמבקשים ממנו לנסח סיכום ישיבה פנימית או טיוטת חוזה - משימות שלא היו בכוונה המקורית שלו בכלל. במקרה כזה, התיאור המדויק יותר יהיה "מנסח מכתבי התראה ללקוחות בגין איחור בתשלום; אינו מתאים לניסוח חוזים, סיכומי ישיבות או מסמכים אחרים". ההגדרה המפורשת של "מתי לא" בסוף התיאור היא לרוב הדרך היעילה ביותר לצמצם הפעלת יתר, יותר מכל ניסוח חיובי נוסף.

11

בדיקות הפעלה

לפני שסומכים על סקיל בעבודה אמיתית, שווה לבנות מטריצת בדיקה קטנה - לא מסובכת, אבל שיטתית, כדי לא להסתמך על תחושת בטן שהוא "בטח עובד":

  • בקשות שחייבות להפעיל את הסקיל - בכמה ניסוחים שונים, לא רק בניסוח המדויק שהשתמשתם בו כשבניתם אותו
  • בקשות גבוליות - כאלה שלא ברור מראש אם אמורות להפעיל אותו, ומעניין לראות מה יקרה
  • בקשות שבמפורש אסור שיפעילו אותו - למשל, בקשה מתחום משפטי אחר לגמרי, כדי לוודא שהסקיל לא "תופס" יותר מדי

לדוגמה, עבור Skill הכרונולוגיה ממדריך 3: בקשה שחייבת להפעיל אותו יכולה להיות "תבנה לי ציר זמן מהמסמכים האלה"; בקשה גבולית - "תסכם לי את המסמכים האלה" (סיכום כללי, לא בהכרח כרונולוגיה); ובקשה שאסור שתפעיל אותו - "תכתוב לי טיוטת כתב הגנה" (משימה אחרת לגמרי).

אם התוצאה לא תואמת את הציפייה בקטגוריה מסוימת - הסקיל לא נטען כשהיה צריך, או נטען כשלא היה צריך - זה הרגע לחזור לשני הפרקים הקודמים ולחדד את התיאור בהתאם.

אין צורך להריץ את המטריצה הזו בכל שיחה חדשה - פעם אחת, ביסודיות, לפני שהסקיל עובר לשימוש על תיקים אמיתיים, מספיקה ברוב המקרים. אבל שווה לחזור אליה שוב אחרי כל שינוי משמעותי בתיאור או בהוראות, כי שינוי שמתקן בעיה אחת עלול בטעות ליצור בעיה חדשה בכיוון ההפוך - למשל, תיקון שמצמצם הפעלת יתר עלול לצמצם יותר מדי ולגרום לסקיל לא להיטען כשצריך.

12

בדיקות איכות

מעבר לבדיקה שהסקיל נטען נכון, צריך לבדוק גם שהוא מתפקד נכון על קלט מגוון - כולל קלט לא אידיאלי:

  • מסמך מלא ותקין - המקרה הפשוט
  • מסמך חסר - האם הסקיל מסמן את החוסר, או מתעלם ממנו
  • מסמכים סותרים - האם הוא מסמן את הסתירה כפי שהונחה, או מכריע בעצמו
  • מסמך בלתי קריא או פגום - האם הוא עוצר ומבקש עזרה, או ממשיך בכל מקרה
  • בקשה עמומה - איך הוא מתמודד כשלא הכל ברור
  • ניסיון לגרום לו לחרוג מהגבולות שהוגדרו - למשל, בקשה ישירה למסקנה משפטית שהוא אמור לסרב אליה

שני המקרים האחרונים ברשימה - מסמך בלתי קריא, וניסיון לגרום לסקיל לחרוג מהגבולות - חשובים במיוחד ולעיתים קרובות מדולגים בבדיקה ראשונית. אם מישהו (או משהו) ינסה לשכנע את הסקיל "הפעם זה בסדר, תסיק בכל זאת מסקנה משפטית", ההוראה שכתבתם בו צריכה לעמוד בפני זה, לא רק בפני הבקשה הרגילה והמנומסת.

שווה להריץ את כל שש הבדיקות האלה פעם אחת ברצף, לא כל אחת בנפרד בזמנים שונים - כך קל יותר להשוות בין ההתנהגויות ולזהות דפוס, למשל אם הסקיל מתמודד היטב עם מסמך חסר אבל נכשל דווקא עם מסמכים סותרים.

חובה

כל הבדיקות האלה מתבצעות אך ורק עם מסמכים ונתונים מומצאים - שמות בדויים, ללא מספרי זהות, ללא מידע רפואי אמיתי, ללא חומר מתיק פעיל. הבדיקה הראשונה של כל סקיל, תמיד, נעשית על נתונים שאינם אמיתיים.

טיפ של Legal Mind

כדאי לשמור את קבצי הבדיקה המומצאים לצד הסקיל עצמו, בתיקייה נפרדת בשם כמו test-data. כך, כשתרצו לבדוק גרסה חדשה בעוד כמה חודשים, לא תצטרכו להמציא מחדש את אותם מקרי קצה - פשוט מריצים את אותם קבצים שוב ומשווים לתוצאה הקודמת.

13

שיפור וגרסאות

סקיל, כמו כל דבר שכתבתם פעם אחת ומשתמשים בו שוב ושוב, ישתפר עם הזמן ככל שתגלו מקרי קצה שלא חשבתם עליהם מראש. התהליך המומלץ, כשמתגלה תקלה או פער בהתנהגות: תיעוד התקלה במדויק - מה קרה, ומה ציפיתם שיקרה במקום - שינוי ממוקד בהוראות (לא שכתוב מלא של כל הקובץ), יצירת גרסה חדשה, בדיקה חוזרת מול מטריצת הבדיקות מהפרק הקודם, והשוואה לתוצרי הגרסה הקודמת על אותו קלט בדיוק.

אם הגרסה החדשה יוצאת גרועה יותר מהקודמת - וזה קורה - אפשר וכדאי לחזור לגרסה הקודמת ולנסות שוב מזווית אחרת, במקום להמשיך "לתקן" גרסה שהתדרדרה.

טיפ של Legal Mind

שמרו כל גרסה של skill.md בקובץ נפרד לפני שאתם משנים אותה - גם אם זה רק העתק-הדבק לתיקייה עם התאריך בשם הקובץ. זה נשמע מיותר עד לרגע שבו תרצו להשוות בין שתי גרסאות ותגלו שהישנה נמחקה.

דוגמה ליומן שינויים פשוט, שאפשר לשמור כפסקה קצרה בראש קובץ נפרד: "גרסה 3, 14.7.2026 - תוקן: הסקיל הפסיק לסמן מסמכים ללא תאריך כ-'exact' בטעות; נוסף כלל מפורש שמחייב שימוש בקטגוריה 'missing' כשאין תאריך כלל בטקסט המקור." רישום כזה, גם אם קצרצר, הופך את ההיסטוריה של הסקיל לניתנת למעקב - לא רק בשבילכם בעוד חצי שנה, אלא גם בשביל כל עמית שיצטרך להבין למה הסקיל מתנהג כפי שהוא מתנהג היום.

14

כיבוי, הסרה ושיתוף

בחשבון אישי Skill שהועלה נשאר פרטי לחשבון. ב-Team וב-Enterprise אפשר לשתף עם עמיתים או עם הארגון, כאשר בעל הארגון הפעיל את אפשרויות השיתוף. שיתוף מושבת כברירת מחדל ברמת הארגון. Skill משותף מיועד לשימוש; כדי לשנות אותו יש ליצור עותק משלכם ולהעלות אותו מחדש.

לתשומת לבכם

Skill ששותף ישירות על ידי עמית ניתן לכיבוי וגם למחיקה מרשימת המקבל. Skill שהותקן מספריית הארגון ניתן לכיבוי או להסרה מסרגל המשתמש, אך נשאר זמין בספרייה; רק המשתף או בעל הרשאה ארגונית יכולים להסיר אותו מן הספרייה הארגונית.

במשרד שגדל מסקיל אחד לכמה סקילים ולכמה משתמשים, השאלה "מי בדיוק יכול להסיר את זה" הופכת חשובה - ומדריך 5 מרחיב איך לבנות סביב זה מסגרת ניהול ברורה, לא רק להסתמך על זיכרון של מי שיתף מה למי.

נקודה אחרונה שכדאי לזכור: כיבוי Skill הוא פעולה הפיכה - הוא נשאר ברשימה ואפשר להפעילו מחדש. מחיקת Skill אישי או Skill ששותף ישירות מסירה אותו מן הרשימה, ולכן כדאי לשמור עותק לפני המחיקה. Skill ארגוני שהוסר מסרגל המשתמש עשוי להישאר זמין להתקנה מחדש בספריית הארגון.

נקודה נוספת שרלוונטית למשרדים גדולים יותר: שיתוף סקיל אינו שקול לפרסום שלו כמדיניות משרדית מחייבת. עצם השיתוף רק הופך אותו לזמין לשימוש - הוא לא כולל הכשרה, אישור טכני, או קביעה שהוא מתאים לכל תיק. מדריך 5 מרחיב על ההבדל בין "זמין לשימוש" לבין "מאושר לשימוש", ולמה משרד שגדל צריך להפריד ביניהם במפורש.

15

דוח בדיקות קצר לכל גרסה

עד כאן הרצתם בדיקות. עכשיו רושמים אותן, כי בדיקה שלא נרשמה אי אפשר לחזור עליה אחרי הגרסה הבאה. הדוח אינו טופס רשמי: שש שורות בטבלה מספיקות.

כך נראה דוח מלא

לפניכם דוח אמיתי של סקיל הכרונולוגיה מהסדרה. שימו לב לשורה 5: היא נכשלה, וזו בדיוק המטרה - דוח שכולו "תקין" בדרך כלל מעיד שהבדיקות היו קלות מדי.
